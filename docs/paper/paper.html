Technical report · ai-locale project · November 2026

Program-Led Chains: Verifiable Multi-Hop Web Question Answering with a Small Language Model as a Bounded Reader

The ai-locale project. Code, prompts, benchmark and run logs are in the project repository (navigatore/catena.py, banco_prova/).

Abstract

Multi-hop questions require following a chain of facts across several sources, each hop guarded by distractors such as homonyms and look-alike candidates. Deep-search agents usually give a large language model (LLM) control of the loop: it decides what to search, what to read and when to stop. We study the opposite division of labour. A deterministic program owns the search: it treats Wikipedia as a graph, reads the open web through a real browser, keeps a global priority frontier over all possible actions, scores candidates and writes the answer line. The LLM (Claude Haiku 5.5, the cheapest model in its family) is used only as a bounded reader for small, closed tasks over numbered rows: propose a plan, name the candidates a row mentions, judge a clue as yes / partly / no / unknown with an exact quotation, extract a typed value. Every model output is checked mechanically (the cited row exists, belongs to the candidate, contains the quoted words, the value has the requested type and range) before it can affect the search.

On a 40-question Italian benchmark of obfuscated 2–4-hop questions synthesised from Wikidata paths (Wikidata itself forbidden at test time), the method answers 36/40 in each of two consecutive full runs (72/80, 90.0%, 95% CI 81.5–94.8%), at a median of 8.6 minutes, 3 web pages and USD 0.11 (API-equivalent) per question. The same model answering from memory scores 9/40 (22.5%); Sonnet 5.5 and Opus 5.5 from memory score 18/40 and 24/40. Over twelve days the accuracy grew from 62.5% (a local-model pipeline) and 70–72% (first chain versions) to 90% almost entirely through program changes, each measured on recorded runs, oracles that need no model calls, or targeted live replays before it was kept. Error analysis shows that most failures were caused by what the program gave the model to read, not by the model's reading. We report the method, the measurements, the rejected interventions and the threats to validity, chief among them that the benchmark was also the development set.

1Introduction

Consider this benchmark question (translated from Italian): “What is the date of birth (day, month and year) of the Brazilian programmer, born in the 1970s, who designed Freedo, the mascot derived from Tux, the penguin of the well-known open-source kernel created in the 1990s?” No page contains the question. The answer requires three hops — Tux → Freedo → its designer → date of birth — and each hop has traps: “Freedo” is also a Swedish music producer, the designer of Tux is an American, and the clues “Brazilian” and “born in the 1970s” are the only things that separate the right person from the wrong ones.

Recent deep-search systems [4, 3, 2, 7] answer such questions by letting an LLM drive a loop of search and reading. This works well with strong models but couples accuracy, cost and safety to the model's judgement at every step: when the model reads too much text it loses the relevant passage [19], when it agrees too easily it accepts the wrong candidate [5], and when it controls the loop a single wrong turn wastes the budget. Our setting adds two constraints. First, the system is a personal assistant whose private documents must never reach a cloud model; for public web research a cloud model is allowed, but it is always called without tools and web text is treated as data, never as instructions. Second, the target is the cheapest model available, so the design must not depend on a strong model's judgement.

We therefore move the logic of the search into the program and keep the model on short, checkable reading tasks. We call this design program-led chains. Our contributions are:

  1. A search architecture in which the program owns planning execution, navigation, scoring and the final answer, and the LLM performs six closed tasks over numbered evidence rows (§3).
  2. A row representation of Wikipedia articles and web pages that keeps the links of every row, so that candidates, verification and values are all tied to a citable row and checked mechanically (§3.3–3.6).
  3. A four-valued, weighted verification with mechanical quotation checks, inspired by [5], and a global best-first frontier over Wikipedia expansions, web expansions and value look-ups across alternative plans, inspired by [6, 1] (§3.6–3.8).
  4. An evaluation on an obfuscated multi-hop benchmark, including closed-book baselines, cost and latency profiles, run-to-run stability and a list of interventions that were measured and rejected (§4–5).
  5. An error analysis showing that, once the model reads few, relevant rows, most remaining errors are attributable to the program and can be fixed without additional model calls (§6).

2Related work

Multi-hop QA over Wikipedia. Benchmarks such as HotpotQA [23] and MuSiQue [24] established multi-hop question answering; retrieval methods follow hyperlinks as a graph [17] or iterate dense retrieval [18]. We adopt the graph view of Wikipedia from [17] but navigate it with a program-controlled frontier rather than a learned retriever, and we leave Wikipedia for the open web whenever an entity has no article.

LLM reasoning on graphs. Think-on-Graph [1] lets an LLM walk a knowledge graph by beam search over numbered candidate relations and entities. We keep the numbered-candidate interface but move the walk and the pruning into the program, and our “graph” is built on the fly from Wikipedia and web pages instead of a curated knowledge base [20, 21].

Deep-search agents. Open Deep Search [4] couples a reasoning agent with a search tool and self-consistency; ManuSearch [3] splits planning, searching and reading among agents and plans each step with keywords and descriptions; HierSearch [2] combines local and web search hierarchically and uses adjacent passages; DeepDive [7] synthesises hard questions from knowledge graphs and trains agents with multi-turn RL; DeepSearch [6] integrates tree search into RL training with a global frontier and depth bonus. We borrow the per-step keywords and descriptions from [3], adjacent passages from [2], alternative plans from [4], KG-based question synthesis from [7] and the global frontier with depth bonus from [6]. Unlike these systems we do no training and never let the model choose the next action.

Claim verification. FEVER [16] framed verification as supported / refuted / not-enough-info against retrieved evidence. WisPaper [5] uses weighted criteria judged as yes / partly / no / unknown with a mandatory quotation and reports that general models answer “yes” too readily. Our verification uses the same four values and weights, but every non-“unknown” judgement must cite a row and an exact quotation that the program checks.

Entity linking. Mapping a name in a row to the right Wikipedia article is entity linking [10, 11, 12, 13, 14, 15]. We use simple, explainable rules (links present in the row, name-in-title, surname fallback, homonym signals such as a name written without a link in a row that links other entities) and measure them with oracles that need no model.

Targeted reading and funnels. Long contexts dilute attention on the relevant passage [19]. DS4A [8] selects target sentences by the type of information sought before reading; the materials-discovery funnel of [9] applies cheap filters before expensive tools. Both ideas shape our row selection (rows containing a value of the requested type are promoted) and our cost ordering (Wikipedia before the web, value look-ups before expansions).

3.2Interpretation and plans

The model first restates the question as three paraphrases and extracts its clues, each referred to the entity it describes. It then proposes a chain plan (JSON with schema): a start entity that the question names with certainty; a list of hops, each with a relation, the type of the target, keywords with which the relation appears in text (in several languages), up to four descriptions to search for the target without knowing its name, and up to six clues with a weight from 1 to 3 (3 = identifies the target almost alone); optional anchors, other named entities from which a later hop can be reached directly; the answer (what is sought, its value type, an optional numeric or year range, and whether the answer is an entity rather than a value); and the search language. A second plan is requested as an alternative to the first. The program adds a third plan when the question mentions an unnamed object (a statue, a painting): the hop through the object is skipped because objects rarely have their own article. All plans share one frontier, so the plan that works advances.

3.3Evidence as rows

Wikipedia articles are fetched through the MediaWiki parse API in the question's language, in English and in the language of the related country, and are split into rows: an infobox line becomes Label: value, a table row becomes cells separated by bars, a paragraph becomes one row per sentence (with care for abbreviations, initials and ordinals), a list item becomes a row. Each row keeps its text, the articles it links to, its kind and its section; references, navigation boxes and sections without facts are removed. Web pages are opened in a headless browser, cleaned and split into blocks; search-result snippets are kept as rows too (§3.4). For a hop, the program sends the model few rows: those containing the hop's keywords, ranked by the rarity of their terms (local TF-IDF), excluding the entity's own name and generic roots, plus rows from adjacent articles that mention the entity [2]. For the value, rows containing a value of the requested type (a full date, a number with a unit, a postal code), and in the requested range, are promoted [8].

3.4Web expansion

When an entity has no article, or Wikipedia yields no candidate, the program expands on the open web. The model writes two or three short queries for the hop; the program passes it the hop's clues and allows one query with a hypothesised name. Results are ranked by the hop's purpose (its relation and target type), not by the whole question, and only the best two to six pages are opened. Search-result snippets that mention the entity enter the evidence at zero page cost, which often suffices to name a candidate or confirm a value. Queries about a candidate always carry a context word from the entity it was found from, to avoid homonyms, and a one-word person name is expanded to the full name found in the evidence (for example Kaia → Kaia Dekker). Value searches try the name with the value's words, the name with context, and the name alone, stopping at the first accepted value. The Arduino question of the benchmark is answered entirely through this path: Arduino → Keyboardio (a keyboard maker inspired by it) → its founder Kaia Dekker (no Wikipedia article) → her spouse Jesse Vincent → 21 June 1976.

3.5Candidates

For each hop the model receives the selected rows and returns candidates, each with the number of the row that names it. The program discards a candidate whose row does not exist, does not contain the name, or names it without a link in a row that links other entities (a strong homonym signal). Variants of the same name are merged, company suffixes (Ltd, S.p.A., Inc, AG) are ignored, and the article of each candidate is resolved from the row's links before any search, so that “Napoli” in a historical row is not mistaken for the city when the row links the Kingdom of Naples.

3.6Four-valued verification with mechanical checks

Each candidate is checked against the hop's clues. The model receives the candidates, each with its own block of rows, and the clues with codes, and answers for each pair one of yes (a row states it about this candidate), partly (only part of it, or indirectly), no (a row contradicts it), unknown (the rows do not say). Every judgement other than unknown must cite a row number and an exact quotation of 3–12 words. The program then checks that (i) the row belongs to that candidate's block, (ii) the row is about the candidate (its article, or its name appears in the row), (iii) the quoted words occur in the row, and (iv) a year required by the clue occurs in the quotation. A failed check turns the judgement into unknown. With Haiku the verification is read twice and a yes survives only if both readings give it.

The quality of a candidate is the weighted mean of its outcomes, with yes = 1, partly = 0.5, unknown = 0 and no = −1. A candidate is strong when its quality exceeds 0.5, its link to the previous entity is proven, and no weight-3 clue lacks evidence; it is refuted when “no” outcomes weigh at least as much as “yes” outcomes on identifying clues; otherwise it is weak and kept in reserve. Links that the program itself recorded in earlier steps are never used as evidence, and a clue that merely repeats the link is not counted twice.

3.7Global frontier

The program keeps one list of all possible actions, across hops and plans: expand a node on Wikipedia, expand it on the web, look up the value of a final node on Wikipedia, or on the web. It repeatedly pops the action with the highest priority. A chain is worth as much as its weakest link, so the path term mixes the minimum and the mean; the depth bonus favours finishing chains; value look-ups have negative cost because they take one call and also act as a check.

priority(a, action) = 0.5 · min(q_path) + 0.5 · mean(q_path) + 0.1 · sqrt(depth(a) / hops) − cost(action) − 0.4 · failures(a) + preference(a) q_path quality of each node on the path; −0.15 if weak; −0.25 if its link is unproven (−0.05 if it only co-occurs with the previous entity); a root counts 0.7 until expanded cost Wikipedia 0 · web 0.35 (0.1 for a node with no article) value on Wikipedia −0.45 · value on the web −0.1

Failed branches lose priority, so the search returns by itself to a reserve candidate of an earlier hop; anchors start closer to the answer and are explored early; plans compete in the same list. The same expansion is never repeated (identical entity, hop and, on Wikipedia, relation), children are reused across plans when the hop is identical, and at most three web value searches are made per parent. A solution's priority is its path quality without the value-search bonus, so a found value does not stop better paths from being finished.

3.8Value, answer and tie-break

For a final node the model returns the value and its row; the program accepts it only if it has the requested type, lies in the requested range and the row is about the entity (the altitude of a neighbouring village does not count). When the answer is an entity (the plan says so), it is accepted only with a proven link of quality ≥ 0.5. When several linked candidates without any “no” are within 0.4 of the best quality, the model is asked to break the tie from their evidence, with the explicit rule never to decide on the asked value itself; the chosen candidate is lifted just above the best. Finally the model writes a short explanation from the cited rows, but the Answer line is written by the program from the accepted value and its source, so the explanation cannot change the answer.

3.9Safety and privacy

The model is invoked through the Claude command-line interface with all tools disabled (claude -p --tools "") and a JSON schema for every task, so it cannot browse, read files or run commands. Web text is cleaned of sentences addressed to an AI system and wrapped in explicit data delimiters. Wikipedia is queried with an identifying User-Agent within Wikimedia's rate limits. Private documents are handled by a separate, local-only path and never reach the cloud model; the chain search operates on public pages only.

4Experimental setup

4.1Benchmark

Following the knowledge-graph synthesis idea of [7], questions were generated automatically from Wikidata: starting from a well-known seed entity (Linux, Galileo Galilei, the Peace of Lodi, …), a path of 2–4 statements is followed and a precise attribute of the last entity is asked (a date, a number with a unit, a name, a postal code). A model writes the question in Italian describing the intermediate entities without naming them. Candidates were then filtered, keeping questions that the local models used by the project (a 4B and a 27B model) answered wrongly from memory, and reviewed. The final set has 40 questions, 10 per theme (computing, history, science, geography and culture). Three questions have more than one valid answer in reality (e.g. a ski resort twinned with two Ligurian villages), so a perfect score is not attainable for a system that picks one.

Example (seed “Monte Bianco”): A reserve of glacial environments protects part of the highest massif of the Alps; the Aosta Valley municipality in which it lies borders a ski resort on the French border, to the south-west. This resort is twinned with a Ligurian seaside village in the province of Savona. What is the postal code of that village? Path: Mont Blanc → Glacial Environments of Mont Blanc → Courmayeur → La Thuile → Laigueglia → 17053.

4.2Protocol and judging

  • Every run uses the real web and live Wikipedia; nothing is cached between runs. Wikidata is blocked at test time because the questions come from it.
  • Per-question budget: 30 web pages, 35 minutes and USD 0.50; three questions run in parallel with separate browser profiles.
  • All model tasks use Claude Haiku 5.5 unless stated. Costs are the API-equivalent costs reported by the Claude CLI.
  • A judge (Claude Haiku, no tools) extracts the single value given as the answer from the Answer line; it is compared with the expected value by normalised string and number matching, and by an LLM equivalence judgement only when matching is inconclusive.
  • Closed-book baselines (§5.2) ask the same question with the instruction to answer from memory with one value and always give the most likely answer; they are judged identically.

Wrong answers are three times as slow and expensive as right ones: they are the runs in which no branch reaches a well-verified value and the frontier explores until the page or time budget ends. This asymmetry makes the budget a useful confidence signal in practice.

5.4Changing the reader

Because the program owns the search, the reader can be swapped without touching it. On the six questions that Haiku had failed in v11b, Claude Sonnet 5.5 solved four (five counting a valid alternative answer), with a stable plan and stricter verification, at about USD 0.74 and 6 minutes per question (2–10 minutes). A local 24B mixture-of-experts model (about 2B active parameters), run through LM Studio with the reasoning block pre-closed and grammar-constrained decoding, produced plans that mixed clues and hops and verifications that accepted almost every candidate (0.92 quality for the American designer of Tux as “Brazilian programmer”); its final answer was wrong with high stated confidence. The bounded-reader design does not rescue a reader that cannot read; it does make a cheap reader that can read sufficient.

6Analysis

6.1Where errors come from

We traced every failure of the earlier runs to the step where the right entity was lost. A representative case is the Galileo question (Galileo → Giuseppe Biancani → Niccolò Zucchi → 6 December 1586). In v11b the plan was right and Haiku's readings were right (“unknown” on “Bolognese Jesuit” for candidates whose rows did not say it), yet the run failed because of the program: a clue that repeated the link was counted twice, so two wrong students became strong; the right one, found by description, stayed weak because no row said “student of Galileo” and was never expanded; two names were linked to the wrong articles through one shared word; the budget ran out on wrong branches. All four causes were fixed in the program (no double counting, strong only with identifying clues proven, title matching through row links, priorities), and Galileo was answered correctly in both final runs.

Across the analysed failures the pattern repeated: when the model received few, relevant rows it usually read them correctly; its errors grew with long, noisy inputs. The fixes that moved the score (Table 2) were therefore almost all program changes: what rows to send, how to link names to articles, how to count evidence, which action to take next and how to search the web for an entity without an article.

6.2Measuring program changes without the model

Live runs are slow, noisy and cost money, so most changes were first measured offline:

  • Oracles without model calls. An entity oracle checks, for names recorded in past runs, whether the program resolves them to the expected article; a row oracle checks whether the gold row of a hop is among the rows the program would send. A change to linking or row selection is kept only if these oracles do not regress.
  • Replays of single model calls. The exact prompt of a past decision is replayed with a changed rule or prompt to see whether the decision changes, at a fraction of a cent.
  • Search-engine probes. The queries a hop would issue are sent to the real search engine and the position of the gold page is recorded, to compare query-building rules.
  • Targeted live replays. Only then is the changed question run live, usually two to five times.

The test suite (568 offline tests with a fake model) guards each rule with the case that motivated it.

7Limitations and threats to validity

  • The benchmark is also the development set. Every rule was motivated by a failure on these 40 questions. Although rules are written to be general, and prompt examples were replaced with unrelated domains after one leaked a benchmark entity, the 90% figure is an optimistic estimate of accuracy on new questions. A held-out set synthesised the same way is the most important next step.
  • Small sample. With 80 question runs the 95% interval is 81.5–94.8%; differences of a few questions between versions are within noise, which is why each final configuration was run twice.
  • Synthetic questions. The questions come from Wikidata paths and are mostly answerable through Wikipedia; real questions about recent or niche topics depend more on the web path, which is exercised by fewer questions (Arduino is the clearest case).
  • LLM judge. A model extracts the answer; one earlier error of the judge (“NOT FOUND” recorded as an answer) was found and fixed. Expected values with several valid answers are judged against one.
  • Non-determinism and drift. Haiku's plans vary between runs; Wikipedia and search results change over time; runs depend on a subscription quota (one run was interrupted and resumed after a usage limit).
  • Language. All questions are in Italian; the method searches in several languages but was tuned on this set.

8Deployment

The method is integrated in the project's desktop application. Every web research that is not marked as private now runs with Claude Haiku as the only model: questions classified as a quick fact go to the chain described here; broader research goes to a concept-map strategy in which Haiku extracts concepts from pages and writes a cited report; when the user leaves the choice to the system, the plan decides between the two. No local model is loaded for web research; local models remain only for private documents and for questions explicitly marked as private, which never reach the cloud model.

Two live checks through the application code on 1 November 2026 (not part of the benchmark statistics): with the mode left to the system, the Arduino question was classified as a quick fact, sent to the chain and answered correctly (21 June 1976; 16.4 minutes, USD 0.22, after a detour through a wrong first candidate company that the frontier abandoned); a broad request on the history of Arduino and the trademark dispute between Arduino LLC and Arduino Srl ran the concept-map strategy for 21.8 minutes and USD 0.54, read 41 sources and produced a cited report in Italian covering the founding at Ivrea, the trademark registrations, the 2015 lawsuits, the 2016 settlement and the 2017 acquisition by the founders' company, flagging where sources disagree.

9Conclusion

A cheap language model can answer obfuscated multi-hop questions reliably when it is asked to read rather than to search. Giving the program the search — rows with links, mechanical checks of every quotation, a global frontier and the final answer line — raised accuracy from 70% to 90% with the same model, made each answer traceable to cited rows, and allowed most improvements to be measured without calling the model. The main open question is generalisation: the next step is a held-out benchmark, including questions whose chains live mostly outside Wikipedia.
